# 文档写作规范

本项目所有文档(guides、advanced、README)遵循本规范。API 参考由 TypeDoc 生成,不在此列。

## 范例

选定 **[react.dev](https://zh-hans.react.dev/learn)** 作为唯一范例:结构照它的 Learn / Reference 分界(即 [Diátaxis](https://diataxis.fr/) 的实践版),语言照它的官方中文版文风。选它的理由:受众相同(React 库的使用者),文风经过大规模读者检验,而且它有中文版,可以直接对照学句子怎么写。

写新页面之前,先去 react.dev 上找一篇同类内容(教程找 [Describing the UI](https://zh-hans.react.dev/learn/describing-the-ui),指南找 [Managing State](https://zh-hans.react.dev/learn/managing-state) 里的单篇,参考找 API 章节任意页),对照它的段落节奏和详略取舍再动笔。

## 页面类型:一篇只做一件事

文档站分三个板块,各配独立侧边栏:`guides`(介绍/快速上手/第一个内容组件)、`advanced`(深入篇章)、`api`(TypeDoc 生成,按 @category 分组)。每篇文档写之前先回答:读者是在**学习**,还是在**干活**?在**动手**,还是在**求解**?答案决定类型与归属板块,类型决定写法:

| 类型 | 本站归属 | 写法 |
|---|---|---|
| 教程(学习) | `guides/quickstart` | 一条连续的路,每步有可见结果,不让读者做选择 |
| 指南(任务) | `advanced/*` | 一篇解决一个问题,标题写目标,讲步骤和边界 |
| 阐释(理解) | `guides/intro` | 讲是什么、为什么这样设计、何时不适用 |
| 参考(查表) | `docs/api`(自动生成) | 干燥、精确、结构可预测,不写叙述 |

判断混了类型的方法:如果某一段拿掉后,页面标题承诺的任务仍然成立,那段就属于别的页面——挪走或删掉。

## 语言规则

- 对读者用"你",现在时,主动语态。动词开头:"创建组件",而不是"你可以创建组件"、"组件将被创建"。
- 每段只讲一件事,段首句给出该段结论。
- 命令、API 名、文件名一律反引号。内联代码里出现尖括号或花括号也要包反引号(MDX 会把 `<T>` 当 JSX 解析)。
- 示例必须对着 `src/public-api.ts` 的现行导出核对过。文档说谎比没有文档更糟。

避免 AI 腔,以下具体禁令:

- 不堆列表。连续超过两个列表就有问题,大部分内容应该用段落讲。
- 不做对称排比("不是 X,而是 Y;既要 A,又要 B"这种成对句式连用)。
- 不写"本文将介绍""让我们来看""总的来说""总而言之"。
- 不用 emoji 和装饰性符号,除非在描述界面上真实存在的图标。
- 加粗只用在真正需要读者扫读时定位的关键词上,一段最多一处,多数段落不该有。
- 标题写成读者会说出口的话("撤销与持久化"),不写营销句("强大而灵活的撤销系统")。

## 提交流程

1. 文档变更与对应代码变更放进同一次提交。改了行为不改文档,review 视为未完成。
2. 提交前跑 `npm run docs`,构建通过才算完成(死链会直接报错)。
3. 链接优先,不复制:通用知识链去权威来源,不在本站重写一份会过时的副本。
4. 默认删除:过期、错误、冗余的内容,拿不准时删掉而不是改写。
5. 拿不准某段该不该存在时,回到类型判定:它帮读者学习、干活、理解、查表,还是只在展示作者的努力?

## 成文自查

- [ ] 这篇属于上表哪种类型?有没有混入第二种?
- [ ] 所有示例都与当前 `public-api.ts` 核对过?
- [ ] 逐段看:有没有可以删的段落?有没有超过两个连续列表?
- [ ] 逐句看:有没有"你可以"、被动句、将来时、AI 腔排比?
- [ ] `npm run docs` 通过?
